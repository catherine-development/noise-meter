| # | Decision | Rationale |

## Work packages

### WP1 — Run identity in the import path (F1, F2, F5) · Fable

Goal: a partial or re-ordered upload can never overwrite or shift a stored run.

1. `noise_db.import_sessions`: upsert runs on `(session_id, source_file)` (index
   `idx_runs_stable` exists); positional fallback only for rows with no `source_file`.
2. Assign `run_number` from the stored session order (sort by `source_file`
   within the session after upsert, renumber). `assessment_runs` already keys on
   `source_file`; WP3 makes reports do the same.
3. Stop writing `sessions.run_count / avg_laeq / max_laeq` from the payload; call
   `recompute_session_aggregates([date])` after the runs land.
4. Surplus rows: `parse_zip` reports per session whether the upload contained a
   complete date folder (`complete_date`); when true, runs absent from the
   payload are deleted; when false they are left alone.
5. Skips become visible: `parse_zip` returns skipped `(path, reason)` entries;
   `do_upload`, `/import` and `import_sdcard.py` surface them. The `>140`
   corruption check looks at every capped channel, not only ch1.
6. `push_to_peer` failures are logged at WARNING and recorded in `sync_state`
   (`last_push_error`), shown on the upload page.

Tests: partial upload preserves the other runs; re-import with a shifted first
run succeeds; assessment link follows the run through renumbering; skipped-file
report is populated; peer-push failure recorded.

**WP1 outcome (branch `worktree-agent-a6c18c3f58b2f3d83`, suite 275/275).**
Built as specified, with these decisions and deviations:

* Schema untouched. `UNIQUE(session_id, run_number)` stays on `runs`; new rows
  are inserted with `run_number NULL` and `_renumber_session_runs()` assigns
  1..n (by `source_file`, then `start_time`, then id) after every import. No
  table rebuild on the Pis.
* `complete_date` semantics are narrower than "delete what is absent": a
  session also carries `skipped_files` (PROJ folders present on the card but
  unreadable), and those are never deleted by a complete-date re-import. F2's
  scenario — first file now fails to parse — therefore keeps PROJ0001.
* Peer payloads (`get_sessions_since`, `get_sessions_export_format`) do **not**
  carry `complete_date`, so a pull or an admin push can only add or refresh
  runs on the receiving Pi, never delete. Deletions from a complete-date upload
  reach the peer only through `do_upload`'s direct `push_to_peer` of the parsed
  payload, which does carry the flag. Conservative on purpose; revisit in WP7.
* `do_upload` still skips a session whose run start times are all already
  stored, so a complete-date upload whose only difference is a *missing* run
  does nothing from the web UI; the deletion path is reachable through
  `/import` (import_sdcard.py `--push`), which has no such pre-check. Safe
  side; flagging rather than changing it here.
* `parse_zip`/`parse_files` return a `ParseResult` (list subclass) with a
  `.skipped` list of `{path, reason, date}`; `/import` returns it as `skipped`,
  `do_upload` appends it to the flash/JSON message (and stays on the upload
  page when there is one), `import_sdcard.py` prints it to stderr.
* `/import` now returns 409 with the constraint text on `IntegrityError`
  instead of 500; `push_to_peer` records `last_push_error` (JSON: at, dates,
  error) in `sync_state`, cleared on the next success, shown on `upload.html`.
  `push_to_peer` returns its thread so the suite can join it.
* Left as-is, deliberately: `update_run_location_tag`, `get_full_run_row`,
  `get_run_prof_laeq` and the `run_tag` sync event are still keyed on
  `run_number`. Numbers are re-read from the database on every render and both
  Pis number a date identically when they hold the same runs; they can diverge
  only while one Pi is missing a run for that date, in which case a synced
  location tag could land on the wrong run. WP4 adds a `source_file` route for
  prof data; carrying `source_file` in the `run_tag` event is a small follow-up.
* Legacy payload rows with no `source_file` still upsert positionally (the
  stored `source_file` is kept via COALESCE). A partial *legacy* payload can
  therefore still overwrite by position — unavoidable without an identity, and
  only pre-2026 JSON exports or an un-upgraded peer produce such rows.
* Merge hazards: the new suite section 4f posts to `/upload` without a CSRF
  token, so WP2's token check will need the test to send one; 4f also edits
  `noise_app.py` (`do_upload`, `do_import`, `upload_page`) and
  `templates/upload.html`, which WP2/WP6 touch too.

## WP2 notes and deviations (Opus)

* **`SESSION_COOKIE_SECURE` is an env flag, default on.** Both Pis are served
  over HTTPS through Cloudflare, so Secure is right there. But
  `deploy_to_pis.sh` advertises `http://192.168.1.116:5001` /
  `http://192.168.1.138:5001` for LAN use, and a Secure cookie is never sent
  over plain http — nobody can stay logged in on those URLs. An instance used
  that way must set `SESSION_COOKIE_SECURE=0` in `.env` and accept that the
  session cookie crosses the LAN in clear. Documented in `.env.example`.
* **The token reaches JavaScript through one shared include, not forty edits.**
  `templates/_csrf.html` publishes the token in a `<meta>` tag and wraps
  `window.fetch` once, adding `X-CSRF-Token` to same-origin non-GET requests.
  Deliberate on two counts: a `fetch()` added anywhere later is protected
  without anyone remembering, and it keeps this package out of WP4's way in
  `index.html`. Real HTML forms still carry a hidden `csrf_token` field.
* **The startup refusal lives in `noise_app`, not in `webauth`'s import.** The
  blueprints need `login_required` at import time, so `webauth` still defines a
  no-op one; `check_startup_security()` is what refuses, called from
  `noise_app` before the app object exists.
* **`test_modules.py` sets `ALLOW_UNAUTHENTICATED=1` at module scope** — the
  suite runs on a Mac with no flight-tracker auth module. Section 8 checks that
  a *subprocess* importing `noise_app` without it still exits non-zero, so the
  refusal is not neutered by the suite's own override.
* **`flask-limiter` was missing from `/tmp/nm-venv` and has been installed
  there.** The app imports it defensively: absent, `/login` and `/upload` are
  unlimited and a warning is logged rather than the app failing to start.
* **Deploy hazard.** The service now *refuses to start* if
  `/home/flightdata/flightdata/auth.py` cannot be imported, where before it
  would have come up serving everything publicly. Check
  `systemctl status noise-app` on both Pis on the first deploy after this
  lands; a failure there is the new behaviour working, not a regression.
* Not changed: `check_upload_auth()` still returns True when `UPLOAD_PASSWORD`
  is empty (now warned about at startup, per the brief); the API key is still
  accepted from a form field as well as the header, for the clients that post
  multipart.

## WP6 notes and deviations (Sonnet)

* **`init_db()` and `startup_sync_from_peer()` moved to module scope**, right
  after `MAX_CONTENT_LENGTH` is set and before the CSRF hook / rate limiter /
  blueprints are wired up, so they run on every import of `noise_app` —
  gunicorn's, `python3 noise_app.py`'s, and the test suite's. Both are
  idempotent (`init_db()` is `CREATE TABLE IF NOT EXISTS` plus additive,
  guarded `ALTER`s; `startup_sync_from_peer()` no-ops without `PEER_URL`/
  `IMPORT_API_KEY`), so this is safe to repeat across the suite's many
  `importlib` re-imports of the module. `sync_peer.py` and `import_sdcard.py`
  import `noise_db` directly, never `noise_app`, so they are unaffected.
  `__main__` now only calls `app.run(...)`.
* **`logging.basicConfig()` is the first executable statement in
  `noise_app.py`**, above even the `config`/`noise_db`/`webauth` imports, so
  it is in effect before those modules' own import-time log calls (e.g.
  `webauth`'s "auth module could not be imported" warning) rather than after.
* **The 413 handler renders inline rather than redirecting**, specifically so
  the response keeps status 413 — a redirect is always a 3xx, which would
  hide the failure from a client that checks the status code instead of
  reading the body. Browser form posts (the ZIP-upload path) get the upload
  page re-rendered with a flash message at 413; `/import`, `/api/*`, and the
  folder-upload `fetch()` call (which now sends `X-Requested-With:
  XMLHttpRequest`, added in `templates/upload.html`, so the handler can tell
  it apart from a plain form post) get a JSON body instead.
* **`get_db()`** now opens with `timeout=15` (SQLite's busy-timeout, so a
  writer waits rather than immediately raising "database is locked" under the
  concurrency gunicorn's 4 threads plus the weather/peer-push background
  threads create) and sets `PRAGMA journal_mode=WAL`. WAL means a running
  database is three files (`noise.db`, `-wal`, `-shm`), which is exactly why
  the backup step uses SQLite's own online-backup API and not `cp` — see
  `backup_db.py`'s docstring for what goes wrong with `cp` and the restore
  command.
* **Backups**: `backup_db.py` is a new, dependency-free script (only
  `sqlite3`/`gzip`/stdlib) rather than shelling out to the `sqlite3` CLI,
  since Gladys and Catherine already run two different Python interpreters
  and there was no reason to also depend on the CLI being on `PATH` for both.
  `setup.sh` installs `noise-backup.service`/`.timer` (daily 03:00, ±10 min
  jitter, `Persistent=true` so a backup still runs if the Pi was off at
  03:00). 14-day local rotation; best-effort `scp` of the newest backup to
  the peer's `/home/flightdata/backups/peer/`, gated on a new `PEER_SSH` env
  var — unset means local-only backups, which is the safe default (no new SSH
  trust relationship implied by just upgrading).
* **`deploy_to_pis.sh`** now runs `/tmp/nm-venv/bin/python3 test_modules.py`
  from `$LOCAL_DIR` before touching either Pi, aborting on failure;
  `--skip-tests` overrides with a printed warning, for when the test venv
  itself isn't available. The file list comes from `git ls-files` (already
  excludes `MEAS118/`, `*.zip`, `.env` via `.gitignore`; the script's own
  `grep -v` filter is defence in depth against a force-add) streamed through
  a single `tar` pipe rather than a hand-maintained `FILES`/`DIRS` pair of
  arrays plus a per-file `scp` loop — this is also what makes new files (like
  `backup_db.py` itself) show up on a Pi automatically. `VERSION` (`git
  rev-parse --short HEAD`) is written to `$REMOTE_DIR/VERSION` on every
  deploy, including `--setup`; `/health` reads it once at import time and
  reports `'dev'` when the file is absent (any checkout not deployed by this
  script, including this worktree). New `--pi Catherine|Gladys` restricts a
  run to one Pi.
* **gunicorn**: exactly 1 worker is load-bearing, not a starting point to
  tune up later — see the comment block above the `ExecStart=` line in
  `setup.sh` for why a second worker would silently double the in-memory rate
  limiter's counters and add a second SQLite writer process. `--threads 4`
  is what actually gives concurrency within that one worker.
* **Not done / left for later**: no `MAX_CONTENT_LENGTH` on the *peer sync*
  paths beyond what Flask already enforces globally (`/api/peer-sync-full`
  responses aren't separately capped — a very large full-sync payload from a
  compromised or buggy peer is still read entirely into memory); no
  structured/JSON log output, `format='%(asctime)s %(levelname)s %(name)s:
  %(message)s')` text only; `noise-backup.timer`'s `RandomizedDelaySec` means
  the exact backup time isn't 03:00 sharp on either Pi, which is intentional
  (avoids both Pis' nightly `scp` to each other landing in the same second)
  but worth knowing if a backup is ever timed against something else.

### WP10 — F6: conflict-safe replication for the mutable tables, + user sync · Fable · **done, not deployed**

Scope: the F6 package from the WP7 design note (`docs/design-note-sessions-and-sync.md`
§3, option 2 + §3.4 — UUID sync keys, LWW with conflict surfacing, delete
tombstones, template replication), plus ongoing replication of the
flight-tracker login users. Base `0d520b4`.

1. `uid` columns (TEXT, unique-indexed) on `assessments`,
   `assessment_locations`, `assessment_runs`, `report_templates`; uid-based
   parent references `assessment_uid` / `location_uid` beside the int FKs;
   `updated_at` maintained on every local mutation; all replication payloads
   and applies key on uids exclusively, resolving to local ids on apply.
2. LWW: an incoming row applies only when its `updated_at` is not older than
   the local row's; stale writes are skipped into `sync_conflicts`
   (latest per uid), exposed at `GET /api/sync-conflicts` (login).
3. `deleted_uids` tombstones written by every local delete of the four
   tables and `generated_reports`; carried in the full payload; applied
   before the upserts; the WP9 report-resurrect gap is closed.
4. Events keep accepting id-keyed payloads from a pre-WP10 peer.
5. `report_templates` replicate (the DEFAULT_TEMPLATES rows unify).
6. `users_sync.py` + `GET /api/users-sync`: additive-only replication of the
   flight tracker's `users` table, pulled each 15-minute tick and at startup.

**WP10 outcome (branch `worktree-agent-a80378ba5978e9e06`, 4 code commits +
tests + docs, suite 673/673, up from 609).** Built as specified; decisions
and deviations:

* **The deterministic uid backfill** (the migration's answer to "both Pis
  already hold the same rows, replicated by id — independent uuid4s would
  twin every one of them on the first full sync"): pre-existing rows get
  `uuid5(F6_NAMESPACE, seed)` where the seed is stable *replicated* content —
  `assessment|created_at|name` for assessments (both fields cross the wire
  and are never rewritten on apply), `location|parent_uid|label|sort_order`,
  `assessment_run|parent_uid|session_date|serial|source_file` (falling back
  to `run:N` for a link that never had a source_file), and
  `template|name|sha256(prompt)` — which is what makes the three seeded
  default templates unify while user templates with different prompts stay
  distinct. Two rows in ONE database with identical seeds are disambiguated
  by id order (`|dup1`, `|dup2`, …) — the ids replicated too, so both Pis
  assign the same suffixes (tested).
  **Risks, stated plainly:** (a) if the pair held *unsynced divergent edits*
  of a seed field (one Pi renamed an assessment and the other never received
  it) at migration time, that row twins — the 15-minute full sync makes this
  a minutes-wide window, and the pre-deploy check below closes it; (b) two
  *genuinely different* assessments created independently on the two Pis in
  the same second with the same name would wrongly unify — accepted as
  vanishingly unlikely, and the unified row keeps one side's content rather
  than losing the record.
* **`updated_at` starts NULL for pre-WP10 rows**, deliberately: NULL sorts
  as "older than everything" in the LWW gate, so the first timestamped edit
  anywhere beats every untouched pre-migration copy, and two NULLs apply
  idempotently (equal timestamps apply too — replays stay idempotent).
* **Conflict semantics.** `sync_conflicts` keeps the *latest* skipped write
  per (table, uid) and is cleared for a uid when a newer incoming row for it
  applies — it shows current divergence, not history. A transient entry can
  appear when this Pi edited a row and the peer's next full payload still
  carries the old copy; it clears as soon as the peer catches up. A delete
  arriving against a row edited *after* the delete also lands here (the row
  survives, the edit re-propagates, and the peer's tombstone is cleared by
  the newer edit — both sides converge on the resurrected row; tested in
  both directions).
* **Tombstones are parent-only for cascades**: deleting an assessment
  tombstones its uid alone — the peer's FK cascade removes the children, and
  an incoming child whose parent uid is tombstoned is skipped rather than
  resurrecting the parent as a stub. Also closed in passing:
  `delete_session` / `purge_sessions_before` / the session-tombstone apply
  now uid-tombstone the `assessment_runs` links they delete, so a stale full
  sync cannot re-create dangling links for a deleted session.
* **Out-of-order events**: a child event arriving before its parent creates
  a stub parent row (`(pending sync)`, `updated_at` NULL) that the real
  upsert fills in place — events are fire-and-forget threads, ordering is
  not guaranteed.
* **Same link created on both Pis while apart**: both sides converge on the
  lexically smaller uid via the stable key
  (assessment, date, serial, source_file), without talking; the tie loser is
  recorded as a conflict for visibility.
* **Mixed-version fallback (why one-pass deploy is still recommended).** An
  id-keyed event or payload row (no uid) applies exactly as before, and the
  inserted/updated row *adopts the deterministic uid the old sender's own
  migration will compute*, so old→new traffic unifies when the old peer
  upgrades. The remaining hole is new→old: a row *created on the upgraded
  Pi* during the window arrives on the old peer by id, and when that peer
  migrates it backfills a deterministic uid where the creator holds a
  uuid4 — that row twins on the next full sync. **Deploy both Pis in one
  pass**: the fallbacks make a mixed pair safe for the deploy window
  (nothing breaks, edits of existing rows behave as today), but rows
  *created* during the window can twin, so keep the window to minutes and
  create nothing in it.
* **Legacy applies do not bump `updated_at`** — an old peer's id-keyed edit
  lands with the local row's timestamp unchanged. Deliberate: stamping
  received data as locally-edited could beat genuinely newer edits
  elsewhere. Transitional-window-only degradation.
* **Templates**: the CRUD routes now mirror upserts/deletes to the peer, and
  clearing the previous default (`is_default=0`) bumps `updated_at` on the
  rows it changes so the peer converges on one default via the full sync
  (the cleared rows are not mirrored as events — the 15-minute pull carries
  them).
* **User sync is additive only — a deliberate scope line.** New users
  propagate (INSERT OR IGNORE on the UNIQUE email); NULL `name`/`phone` on
  an existing row are COALESCE-filled; **nothing else about an existing row
  is ever touched: no LWW, no deletes, and no `is_active` propagation.
  Deactivating a user is a per-Pi manual act, and a user deactivated on one
  Pi REMAINS ACTIVE ON THE PEER** until someone deactivates them there too —
  do both by hand until the flight tracker owns replication. `id` and
  `invited_by` (a local-id reference) never cross the wire; the column set

  through. Every function is a clean no-op when the flights DB or its
  `users` table is absent (dev Mac, suite) and never creates the file.
  PII: emails/phones transit only the authenticated HTTPS channel; the logs
  carry counts only.
* **Not done / later**: no UI page for conflicts (the JSON endpoint is the
  deliverable; a Manage-page table is a later nicety); `sync_conflicts` rows
  for a uid that never converges persist until a newer apply clears them —
  no expiry; assessments URLs and events still carry local ids for display
  and old-peer compatibility (harmless — applies ignore them when a uid is
  present).

### WP11 — Import safety: explicit prune, link hygiene, ZIP limits (F1, F5, F8a) · Fable · **done, not deployed**

Scope: the three verified findings from the independent (Codex) review.
Base `92b65b2` (production-fixes; suite baseline 673). Suite after: **705**.

**F1 (critical) — completeness is now explicit, never inferred.**
`parse_zip`/`parse_files` no longer derive `complete_date` from path shape
(they always emit `False`): a ZIP of one PROJ folder zipped from its parent
carries `YYMMDD/PART0000/PROJnnnn/…` paths while holding a fraction of the
day, and `import_sessions` then deleted every other stored run for the date
(reproduced: 3 runs became 1). Deletion now happens only when a caller
explicitly authorises it:

* **`import_sdcard.py`** walks the real card root, so it is the one caller
  that can honestly claim completeness: it stamps `complete_date: True`
  itself (`mark_complete_dates()`) on the dates it fully enumerated and
  sends top-level `"prune": true` in its push (and in `--output` files).
  New `--no-prune` flag disables both.
* **Web upload**: a new checkbox on the upload form — "This upload is the
  complete SD card for its date(s): remove stored runs missing from it" —
  default OFF, posted as `prune=1`. `do_upload` stamps `complete_date` only
  when it is checked (and strips it from .json uploads when it is not).
  Every prune outcome is reported and shown on the upload page (the index
  shows no flashes): which runs were removed, how many assessment
  assignments went with them, or "No stored runs needed removing."
  A prune upload bypasses the `_has_new_runs` pre-check, so an upload whose
  only difference is a *missing* run still prunes (closing the WP1 note
  that the deletion path was unreachable from the web UI).
* **`/import`** honours a per-session `complete_date` only when the request
  carries the top-level authorisation — `"prune": true` in a JSON body, or
  `?prune=1` / form `prune=1` beside a raw ZIP — so an old peer, old
  exporter, or a replayed pre-WP11 JSON file (which captured the inferred
  flag) can never delete anything. `get_sessions_since` /
  `get_sessions_export_format` still omit the keys entirely (asserted).
* **`peer_client.push_to_peer(sessions, prune=False)`** forwards the
  operator's authorisation as the payload's top-level `"prune": true`, so a
  prune from the upload form lands on both Pis. Without this the peer's
  copy of the pruned runs would resurrect locally on the next 15-minute
  pull. *Note: this is a small, additive edit to `peer_client.py`, which
  WP12 is also editing — see merge hazards.*

`skipped_files` (PROJ folders present but unreadable) keeps its WP1 role:
an explicit prune still never deletes a run whose file merely failed to
parse.

**F5 (high) — no more dangling assessment links.** When the complete-date
branch of `import_sessions` prunes runs, it now — in the same transaction —
deletes each pruned run's `assessment_runs` rows via the stable key
(session_date, instrument_serial, source_file) and writes a WP10 uid
tombstone for each (`record_uid_tombstones`, exactly as `delete_session`
does), so the removal replicates and a stale full sync cannot resurrect the
link. `import_sessions` returns an `ImportResult` (an `int` subclass, so
every existing caller is unchanged) carrying `deleted_runs`,
`deleted_links` and `deleted_run_files`; `do_upload` and `/import` surface
them — an assessor is told when the packaging of their evidence changed.
Legacy runs with no `source_file` have no stable key to match; their links,
if any, remain what `audit_assessment_run_keys()` reports.

**F8a (medium) — decompression limits.** `parse_zip` (and therefore
`parse_files`, which routes through it) refuses, before extracting
anything: more than 4,096 members; any member declaring > 32 MB
uncompressed; > 512 MB declared in total; or a member whose stream runs
past its declared size — each member is read through a capped stream
(`fh.read(declared+1)`), never a blind `.read()`, since declared sizes can
lie. Refusals are `ValueError`s with readable messages; `do_upload` shows
them as the existing "Could not read file" flash and `/import` returns 400
`import refused: …` (previously an unhandled 500). Duplicate member names
were silently last-one-wins; the first copy now wins and the rest are
reported in the skip list.

**Existing checks changed, deliberately (both in section 4f):**
1. "session marks PROJ0002 as present-but-unreadable" asserted
   `complete_date is True` for a date-folder ZIP — the inference under
   test *is* F1; it now asserts `False`.
2. "complete-date import over /import deletes absent runs" — split in two:
   the same POST without prune now deletes nothing (and reports
   `deleted_runs: 0`), and a second POST with `?prune=1` performs the old
   deletion while keeping the skipped-but-present run.

**Tests**: new section 17 (29 checks) — the exact F1 repro against a 3-run
session; /import ignoring a payload's own `complete_date`; the prune

2. Mixed-version window: a pre-WP11 Pi's `/import` still honours

### WP13 — report output sanitizing and BS 4142 prompt corrections · Opus · **done, not deployed**

Two findings from the independent (Codex) review of `92b65b2`, both verified
before the fix. Base `92b65b2` (`production-fixes` tip); branch
`worktree-agent-aa403ab3f440e1cf5`; suite **735 checks, up from 673**.
Numbering note: Codex's F6/F7 are not the F6/F7 of the original production
review — Codex F6 is the stored-XSS finding, Codex F7 the BS 4142 one.

**Codex F6 (High, stored XSS).** All six report sections render with `| safe`.
They are HTML the model writes from a prompt that embeds user-controlled text
(session notes, location, recorder name, assessment metadata), so a prompt
injection — or a hostile row arriving over the peer sync — put executable HTML
into an evidence document on both Pis. Confirmed by storing
`<img src=x onerror=…>` and seeing it come back unescaped.

* New module `html_sanitize.py`, stdlib only (`html.parser`). Allowlist:
  `p br ul ol li table thead tbody tr th td h1..h4 strong em b i u span div
  blockquote code pre`. Every attribute is stripped except `colspan`/`rowspan`
  on `th`/`td`, and those are re-emitted from a parsed integer (1–100), so no
  attacker-controlled text reaches the output at all. A disallowed tag is
  dropped but its text is kept; `script`/`style`/`iframe`/`object`/`embed` are
  dropped whole. Comments, PIs and doctypes go. Entity and character
  references are re-emitted verbatim (`&nbsp;`, `&#8211;` survive an evidence
  document unchanged). Unclosed and mis-nested tags are closed for you.
  Nothing raises: a parser failure returns `html.escape()` of the input.
* Applied in `reports.api_generate_report` before `save_generated_report`, so
  what is stored — and what replicates to the peer — is already clean, and
  again in `reports.view_report` on every section before render, which is the
  line that covers legacy rows and rows that arrived through
  `sync_db._apply_generated_report` (it upserts the sections blob verbatim;
  that file belongs to WP12 and was not touched here).
* `| safe` stays — the sanitizer is what makes it safe — with a Jinja comment
  in `templates/report.html` saying so.
* **No class survives sanitizing.** The stylesheet's `.band*`, `.td-hi` and
  `.td-ok` rules are unreachable from model HTML, and were already: nothing in
  any prompt tells the model those class names exist. `.prose` styling targets
  element names (`.prose p`, `.prose table`, …) and is unaffected. The CSS is
  left in place — the app's own table markup uses `.td-hi`/`.td-ok`.

**Legacy rows: sanitized at render, not rewritten in the database.** Nine
stored reports across the two live databases predate this. Deliberate choice:
(a) a generated report is evidence, and rewriting its stored bytes in a
migration would silently alter a document that may already have been printed
and filed — the render-time filter changes what is *displayed* without
touching the record; (b) the render-time filter is needed anyway, because
peer-replicated rows arrive unsanitized regardless of what a one-off migration
did; a save-time-only fix would leave that hole open. The cost is that the raw
`sections_json` on disk still contains whatever was stored, so anything that
renders it *without* going through `view_report` would be unprotected — today
nothing does (the JSON API returns the listing rows only, and
`input_snapshot_json` holds figures, not HTML). If Catherine would rather have
the stored bytes cleaned too, it is a five-line migration over
`generated_reports`, and the two paths are not exclusive.

**CSP: report view only, nonce-based.** `GET /reports/<id>` now sends

```
default-src 'none'; script-src 'nonce-<per-response>'; style-src 'nonce-<per-response>';
img-src 'self' data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

A nonce rather than `'unsafe-inline'`, because `'unsafe-inline'` would permit
exactly the injected inline script the sanitizer exists to stop; with a nonce
in `script-src`, inline event handler attributes are blocked outright too. To
make that possible the page had to stop relying on inline attributes:
`onclick="window.print()"` became a nonced listener on `#printBtn`, and the
two `style="…"` attributes became the `.stat-val.duration` and `.table-note`
classes. `templates/_csrf.html` gained
`<script{% if csp_nonce %} nonce="…"{% endif %}>` — `csp_nonce` is undefined
on every other page, and Jinja's Undefined is falsy, so those pages render
byte-identically to before. **No global CSP**: `index.html` is inline JS
throughout and would break.

**Codex F7 (High, standards correctness).** BS 4142:2014+A1:2019 compares the
**rating level** — specific sound level plus character corrections — against
the background, not the specific level. The Local Government Enforcement
template said "difference between specific noise level and background LA90";
the Occupational one said "significance criteria relative to LA90 background".
Both now derive a rating level, naming tonality, impulsivity, intermittency
and any other distinctive characteristic with the dB applied, keep the
+5/+10 interpretation (now rating-vs-background, read in context), and carry
the caveat that corrections are the assessor's on-site judgement, not an
instrument reading: state each as an explicit assumption, take the rating
level as the specific level where none can be justified, never invent one.
The Planning template was already correct and gained only the naming +
assumption sentence. Every other clause is byte-identical.

Weather: `_build_session_data_block` now emits `Weather (archived regional
data — Open-Meteo, not an on-site observation): …`, and each of the three
templates gained one sentence saying that line is context only, that on-site
meteorological conditions were not recorded unless the notes say so, and that
BS 4142 conclusions must flag the limitation. The report page still shows the
same `wx_str` under "Weather conditions".

**Refreshing the templates already on the Pis.** The seed only runs on an
empty `report_templates`, so editing `DEFAULT_TEMPLATES` alone would have
changed nothing on either Pi. `reports_db.refresh_default_templates(conn)`,
called from `noise_db._migrate` immediately after the seed block, rewrites a
stored row whose prompt is byte-identical to a text this repo once shipped

`PREVIOUS_DEFAULT_PROMPT_SHA256`, so a Pi still on a pre-`17288f0` prompt is

Three deliberate details:

* `updated_at` is set to the **fixed** `2026-08-20 00:00:00`, not

* It runs **before** the WP10 uid backfill, so the deterministic template uid

  first and WP13 later, the pair instead keeps the uid computed from the old

  third, fresh Pi joining after a WP10-then-WP13 sequence would differ.
* Idempotent: a row already carrying the current text is skipped, so a second
  migration pass writes nothing and does not re-stamp `updated_at`.

### WP12 — replication ordering: watermark, total-order LWW, metadata under LWW, bounded report shipping (F2, F3, F4, F8b) · Fable · **done, not deployed**

Scope: the four ordering findings from the independent (Codex) review of
`92b65b2`. Base `92b65b2` (post-WP10, "All 673 checks passed"); suite now
**721/721** (section 18, four sub-sections, one per finding).

**F2 — the measurement watermark is now the sender's clock.**
`GET /api/sync` returns `server_now`: the sender's own `datetime('now')`
(UTC, the same clock and format that stamps its `imported_at`).
`sync_peer.py` stores THAT as the watermark instead of its own wall clock,
so clock skew between the Pis can no longer strand a session permanently
behind the watermark — the old scheme compared the sender's `imported_at`
(strict `>`) against a receiver-clock timestamp, and the full-sync payload
carries no measurement sessions, so a missed session was missed forever.
The request's `since` is the stored watermark minus a 300 s overlap
(`sync_db.request_since`), reformatted to the `imported_at` convention;
`get_sessions_since` compares with `>=`. Re-receiving the overlap is
harmless — `import_sessions` is a stable-key idempotent upsert. In passing
this also fixes a format bug the review's scenario implied: the old
watermark was ISO **'T'-separated** while `imported_at` is space-separated,
and `'T' > ' '` in a string compare, so the old `since` ordered *after
every same-day `imported_at`* — the pull leg could never deliver a
same-day session at all (the push leg masked this). `request_since`
parses both formats, so the first post-deploy pull heals the stored
watermark transparently.

**F3 — total-order LWW.** Every LWW timestamp (`updated_at` on
assessments / assessment_locations / assessment_runs / report_templates,
and `deleted_uids.deleted_at`) is now written at millisecond resolution
(`noise_db.LWW_NOW_SQL` = `strftime('%Y-%m-%d %H:%M:%f','now')`), and
every local mutation also stamps `writer` (the Pi's `PI_NAME`, read at
call time). The gate compares the string tuple `(updated_at, writer)`:
strictly greater applies, strictly smaller skips into `sync_conflicts`,
**exactly equal is a no-op** — WP10 applied equal timestamps, which is
what made two Pis editing one row in the same second swap values on every
exchange, forever, with zero conflict records. Transition semantics,
verified in tests: stored second-resolution timestamps stay valid
(`'…SS'` string-orders before any same-second `'…SS.mmm'`); a row without
a writer compares as `''` and loses same-timestamp ties to any named
writer; and an equal-timestamp incoming row with an empty writer is
treated as a pre-WP12 peer echoing our own write back (it stores our
timestamp but has no writer column) — a no-op, not a recorded conflict.
Delete-vs-edit stays timestamp-only: an exact tie is delete-wins on both
sides, so tombstones need no writer to converge.

**F4 — session metadata and run tags under LWW.** New columns (additive):
`sessions.meta_updated_at/meta_writer`, `runs.tag_updated_at/tag_writer`,
NULL for existing rows on purpose (NULL = "never hand-edited since WP12").
`update_session_metadata` / `update_run_location_tag` stamp them and
return the stamps; the `session_meta` / `run_tag` events and the full
payload carry them; applies go through the same tuple gate
(`sync_db._apply_session_meta` / `_apply_run_tag`), with conflicts in
`sync_conflicts` under table_name `'session_meta'` (uid `date|serial`)
and `'run_tag'` (uid `date|serial|source_file`). Rules: stamped beats
unstamped **without** a conflict (unstamped data has no ordering claim to
record); unstamped-on-unstamped keeps the exact pre-WP12 behaviour
(COALESCE merge from the full payload, plain overwrite from an event), so
an old peer and never-edited rows behave as today. A stamped winner
overwrites all six metadata fields including NULLs — an edit that cleared
a field clears it on the peer too — and a **cleared run tag now
replicates** (the full payload includes stamped-but-NULL tag rows; the
old `WHERE location_tag IS NOT NULL` + COALESCE merge could never
propagate a clear). `import_sessions`' metadata COALESCE is deliberately
untouched: an SD/measurement payload carries no metadata keys, so
`COALESCE(excluded, stored)` keeps every stored value — a re-import
cannot clobber a hand edit (tested). **Residual, stated plainly:** that
COALESCE prefers a *non-NULL payload* value, and peer measurement-session
payloads do carry the peer's metadata copy — so a session pull from a
peer that has not yet received a hand edit can still reapply the older
values through the measurement path, outside the meta-stamp gate (the
stamps are not regressed, so the loss is silent). Pre-existing behaviour,
unchanged in kind; follow-up candidate: have `import_sessions` skip the
metadata columns when the stored row carries a newer `meta_updated_at`
(not done here — WP11 owns `import_sessions` concurrently).

**F8b — bounded report shipping.** `GET /api/peer-sync-full?light=1`
replaces `generated_reports` (each row carrying its full `sections_json`
and `input_snapshot_json`, shipped every 15 minutes forever) with
`generated_reports_digest`: `{uid, created_at}` per report. The tick
(`sync_peer.py`) pulls light, diffs the digest against local uids
(`sync_db.report_uids_to_fetch` — locally tombstoned uids are excluded,
so a deleted report is not re-downloaded every tick), and fetches only
missing/changed rows through the new `GET /api/reports-sync?uids=…`
(`require_api_key`, batch capped at `REPORTS_SYNC_MAX` = 100; the puller
chunks at the same size). The startup sync keeps the full payload (rare,
so bounded). Templates stay full-bodied in light mode — they are small.

**Existing checks changed (deliberately):** none fail and none were
weakened; the only edit is the section-16 comment above "the winning
apply cleared any stale conflict entry on A", which described the old
equal-timestamps-apply rule — a replayed equal row is now a no-op (and
the check still holds). No existing check asserted the metadata-COALESCE
oscillation directly, so nothing there needed rewriting; section 18c now
pins the new convergent behaviour.

#### Mixed-version tolerance (one-pass deploy window, and after)

The fallbacks are designed so a mixed pair degrades to **pre-WP12
behaviour, never worse**; what that means precisely, per finding
(N = upgraded Pi, O = not yet):

* **F2**: N pulling O — O sends no `server_now`, N falls back to its own
  clock (the pre-WP12 hazard persists for that leg until O upgrades; N's
  requests are already space-formatted with the overlap, which is
  strictly better). O pulling N — O's old 'T' watermark and local clock
  behave exactly as today (`>=` vs `>` is the only sender-side change).
  After both upgrade, `request_since` parses the stored old-format
  watermark, so the transition heals itself on the first tick.
* **F3**: N's millisecond+writer stamps flow into O's `updated_at` TEXT
  verbatim and string-compare chronologically; O's edits arrive at N as
  second-resolution, writerless — documented old-format semantics, i.e.
  the same-second hazard persists only for O-authored edits during the
  window. O's full payload echoes N's rows back without `writer` (its
  schema has no column); the equal-timestamp writerless echo rule makes
  those no-ops instead of spurious conflicts.
* **F4**: events/payloads in both directions stay compatible (extra
  stamp keys are unbound named parameters on O; missing stamps on N take
  the unstamped path). The one real window degradation: **a metadata or
  run-tag hand edit made on O loses silently to any stamped edit N has
  ever made to that row** (stamped-beats-unstamped, no conflict). Edits
  N makes reach O as plain overwrites, as today. Practical rule: during

* **F8b**: no degradation in either direction. O ignores `?light=1` and
  returns the full payload (N applies it — the digest handling is
  additive); O never asks for light and N serves it the full payload.
  The bandwidth saving simply starts when both are upgraded.
* **Migration**: additive `ALTER TABLE` only (six columns), no rebuild,
  no backfill. Old and new schema coexist on the wire throughout.

### WP14 — separating operator restoration from peer replay (F1, F2, F3, F4) · Fable · **done, not deployed**

Scope: the four verified findings from the second independent review of
`44761fd` (`production-fixes` tip, post-WP12/WP13; suite baseline 815).
Suite after: **850/850** (section 20, four sub-sections, one per finding).
WP12's own "Residual, stated plainly" note *is* F1 — this package closes it.

**F1 (High) — the measurement path can no longer bypass the meta stamp
gate.** A peer measurement pull went through `import_sessions`, whose
metadata COALESCE overwrote non-null stored values WITHOUT touching
`meta_updated_at`/`meta_writer` — reproduced: a newer hand edit was
replaced by the peer's stale copy, which then carried the newer stamp, so
the corruption replicated everywhere as the apparent LWW winner.
`import_sessions` now takes an explicit `origin`, and `get_sessions_since`
carries `imported_at` + `meta_updated_at`/`meta_writer` per session, so
peer-pulled metadata arrives with its LWW claim attached and is applied
through the same ordering rules as the `session_meta` gate
(`noise_db._replay_session_meta` — no conflict bookkeeping there; the
15-minute full-sync tick routes the same row through the real gate, which
records losers). Operator imports keep the fill-and-overwrite COALESCE and
now **stamp the change** (only when a stored value actually changed — no
phantom edits), so an operator import is a first-class LWW write that
replicates correctly instead of silently diverging.

**F2 (High) — a tombstone yields only to proof or to an operator.**
`import_sessions` deleted the session tombstone unconditionally
("importing supersedes deletion"), so WP12's deliberate 5-minute watermark
overlap let a peer replay resurrect a recently-imported-then-deleted
session (reproduced: 0 sessions/1 tombstone → 1 session/0 tombstones). Now
a peer-origin import skips a tombstoned `(date, serial)` entirely unless
the payload's own `imported_at` (the sender's clock) is `>=` the
tombstone's `deleted_at` — the exact convention `_apply_tombstones` uses
in the other direction (session-wins-ties), so both Pis pick the same
survivor. A stampless payload (old peer, no `imported_at` key) can never
resurrect. Operator imports and their immediate relay still clear the
tombstone: re-importing a deleted date is a deliberate restoration, and
both Pis must converge on restored. `purge_sessions_before` and
`_apply_tombstones` were checked and left as they are — the peer-side
comparison added here mirrors them; nothing else changed in kind.

#### The origin decision table

Every caller of `import_sessions` now declares who is speaking:

| origin | who sends it | session tombstone | metadata columns | meta stamps |
| --- | --- | --- | --- | --- |
| `operator` (default) | web upload (`do_upload`), `import_sdcard.py` → `/import`, any `/import` payload naming no origin | **cleared** — deliberate restoration | COALESCE fill-and-overwrite (payload non-null wins), as always | **stamped when a value actually changed** (`LWW_NOW_SQL` + `PI_NAME`) — the edit then replicates through the `session_meta` gate |
| `operator-relay` | `push_to_peer`'s payload (`"origin": "operator-relay"`): `do_upload`'s immediate relay of a fresh import, `/admin/push-to-peer` | **cleared** — the operator restored the date; the peer must converge on restored, or its next full sync would re-delete the restoration | replay rules (below) — in practice a no-op: relayed parser/export payloads carry no metadata | **never** — the operator's edit was stamped once, on the Pi where it happened, and replicates through the gate, not as a second competing edit |
| `peer` | `sync_peer.py`'s 15-minute pull; a push whose payload says `"origin": "peer"` | **respected** — session skipped unless payload `imported_at >= deleted_at` (proof the copy postdates the deletion; then the tombstone clears and the row restores) | stamped payload → LWW tuple compare, strictly-newer wins whole (all six fields + stamps); stampless payload → fill-NULL-only, and never into a row that carries a stamp | only carried through when the incoming stamped copy wins |

Guiding principle, stated once: **an operator action (and its immediate
relay) may restore a deletion and may write metadata as a stamped edit —
exactly once, on the Pi where it happened, with replication carrying it as
a normal LWW write; mechanical replay may never override a stamped edit
and never resurrect a deletion it cannot prove is stale.**

`/import` honours the payload's `origin` because every `/import` request
is API-key-authenticated (`@require_api_key`) — only the peer or the
operator's own tooling holds the key. A ZIP body is always `operator`.

**F3 (Medium) — the startup sync is bounded.** `startup_sync_from_peer`
still fetched the plain `/api/peer-sync-full` — every report body, every
restart, forever: the one unbounded transfer left after WP12. The tick's
light pull (light payload → digest diff → chunked by-uid report fetch at
`REPORTS_SYNC_MAX`, old-peer fallback to the full payload) moved into
`sync_db.pull_full_sync_from_peer()`, shared by `sync_peer.py` (30 s light
timeout, as before) and `peer_client.startup_sync_from_peer` (its original
15 s light timeout; the chunked fetches keep their own 30 s). No circular
import: `sync_db` already sits below both callers.

**F4 (Medium) — peer clock skew is now observable.** Ordinary LWW ordering
is wall-clock, so a Pi whose clock runs slow loses edits it genuinely made
later — silently. Full logical clocks are out of scope; this is the
monitoring hook: every tick, `sync_peer.py` measures
`skew_s = local UTC now − server_now` (coarse by design — transfer time
and second resolution included) via `sync_db.record_peer_clock_skew`,
stores `{skew_s, at}` in `sync_state` under `peer_clock_skew_s`, logs a
WARNING when |skew| > `CLOCK_SKEW_WARN_S` (30 s), and `/health` exposes
`peer_clock_skew_s`/`peer_clock_skew_at` (null until measured, or when the
peer predates `server_now`). **LWW correctness degrades with skew; watch
this number.**

**Existing checks changed, deliberately (both source-grep checks; no
behavioural check was weakened):**
1. Section 15's "sync_peer.py gap-fills right after importing the pull" —
   the grepped substring is now `= import_sessions(sessions,
   origin='peer')`.
2. Section 18d's "the 15-minute tick pulls light and fetches the digest
   gaps" — the endpoints moved into `sync_db.pull_full_sync_from_peer`;
   the check now asserts the tick calls the helper and the endpoints live
   in `sync_db`.
No section 4/17/18 behavioural check encoded the unconditional tombstone
clear or the unstamped overwrite from a *peer* context — section 5c's
"re-import clears the tombstone" and 18c's "SD re-import does not clobber
a newer hand edit" are operator-path checks and still pass unchanged;
section 20 pins the new peer-path behaviour beside them.

**Tests**: section 20 (35 checks) — the exact F1 repro (newer stamped hand
edit survives a peer measurement replay, values AND stamps untouched; the
operator path does update and stamp; a metadata-less re-import bumps
nothing); F2 both ways (replay inside the overlap window does not

#### Mixed-version window (one-pass deploy, and after)

* **Old peer's push → new Pi**: a pre-WP14 `push_to_peer` sends no
  `origin`, so its push imports as `operator` — tombstones cleared,
  COALESCE overwrite (now stamped when it changes something). This is
  **exactly today's behaviour**, i.e. the F1/F2 hazards persist for that
  leg until the peer upgrades — acceptable because the window is one
  deploy pass and the degradation is precisely the status quo, never
  worse.
* **New Pi's pull ← old peer**: the old peer's `/api/sync` payload carries
  no `imported_at`/meta stamps. The new Pi's `origin='peer'` import then
  takes the conservative fallbacks by construction: fill-NULL-only
  metadata, no resurrection ever. Strictly better than today.
* **New Pi's push → old peer**: the old `/import` ignores the unknown
  `origin` key — plain operator import, today's behaviour.
* **Startup/tick pulls**: unchanged compatibility from WP12 — an old peer
  ignores `?light=1` and serves the full payload, which the shared helper
  applies (the fallback is tested).
* **Skew**: an old peer sends no `server_now` → nothing measured,
  `/health` shows null (or the last dated measurement). No degradation.
* **Migration**: none. No schema change, no stored-data rewrite; the new
  wire keys are additive and ignored by old receivers.
