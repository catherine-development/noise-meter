## Decisions taken (reversible — say so if you disagree)

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | Partial uploads (a single PROJ folder / flat DAT pair) stay supported, and WP1 makes them safe. | The upload page advertises them; the fix is to key runs correctly, not to remove the feature. |
| D2 | The stored session LAeq becomes **duration-weighted** (by `duration_s`, falling back to `n`). | It is the physically meaningful combination and the report already uses it; one definition everywhere. History chart will move for mixed-length days. |

## Work packages

### WP1 — Run identity in the import path (F1, F2, F5) · Fable

Goal: a partial or re-ordered upload can never overwrite or shift a stored run.

1. `noise_db.import_sessions`: upsert runs on `(session_id, source_file)` (index
   `idx_runs_stable` exists); positional fallback only for rows with no `source_file`.
2. Assign `run_number` from the stored session order (sort by `source_file`
   within the session after upsert, renumber). `assessment_runs` already keys on
   `source_file`; WP3 makes reports do the same.
3. Stop writing `sessions.run_count / avg_laeq / max_laeq` from the payload; call
   `recompute_session_aggregates([date])` after the runs land.
4. Surplus rows: `parse_zip` reports per session whether the upload contained a
   complete date folder (`complete_date`); when true, runs absent from the
   payload are deleted; when false they are left alone.
5. Skips become visible: `parse_zip` returns skipped `(path, reason)` entries;
   `do_upload`, `/import` and `import_sdcard.py` surface them. The `>140`
   corruption check looks at every capped channel, not only ch1.
6. `push_to_peer` failures are logged at WARNING and recorded in `sync_state`
   (`last_push_error`), shown on the upload page.

Tests: partial upload preserves the other runs; re-import with a shifted first
run succeeds; assessment link follows the run through renumbering; skipped-file
report is populated; peer-push failure recorded.

**WP1 outcome (branch `worktree-agent-a6c18c3f58b2f3d83`, suite 275/275).**
Built as specified, with these decisions and deviations:

* Schema untouched. `UNIQUE(session_id, run_number)` stays on `runs`; new rows
  are inserted with `run_number NULL` and `_renumber_session_runs()` assigns
  1..n (by `source_file`, then `start_time`, then id) after every import. No
  table rebuild on the Pis.
* `complete_date` semantics are narrower than "delete what is absent": a
  session also carries `skipped_files` (PROJ folders present on the card but
  unreadable), and those are never deleted by a complete-date re-import. F2's
  scenario — first file now fails to parse — therefore keeps PROJ0001.
* Peer payloads (`get_sessions_since`, `get_sessions_export_format`) do **not**
  carry `complete_date`, so a pull or an admin push can only add or refresh
  runs on the receiving Pi, never delete. Deletions from a complete-date upload
  reach the peer only through `do_upload`'s direct `push_to_peer` of the parsed
  payload, which does carry the flag. Conservative on purpose; revisit in WP7.
* `do_upload` still skips a session whose run start times are all already
  stored, so a complete-date upload whose only difference is a *missing* run
  does nothing from the web UI; the deletion path is reachable through
  `/import` (import_sdcard.py `--push`), which has no such pre-check. Safe
  side; flagging rather than changing it here.
* `parse_zip`/`parse_files` return a `ParseResult` (list subclass) with a
  `.skipped` list of `{path, reason, date}`; `/import` returns it as `skipped`,
  `do_upload` appends it to the flash/JSON message (and stays on the upload
  page when there is one), `import_sdcard.py` prints it to stderr.
* `/import` now returns 409 with the constraint text on `IntegrityError`
  instead of 500; `push_to_peer` records `last_push_error` (JSON: at, dates,
  error) in `sync_state`, cleared on the next success, shown on `upload.html`.
  `push_to_peer` returns its thread so the suite can join it.
* Left as-is, deliberately: `update_run_location_tag`, `get_full_run_row`,
  `get_run_prof_laeq` and the `run_tag` sync event are still keyed on
  `run_number`. Numbers are re-read from the database on every render and both
  Pis number a date identically when they hold the same runs; they can diverge
  only while one Pi is missing a run for that date, in which case a synced
  location tag could land on the wrong run. WP4 adds a `source_file` route for
  prof data; carrying `source_file` in the `run_tag` event is a small follow-up.
* Legacy payload rows with no `source_file` still upsert positionally (the
  stored `source_file` is kept via COALESCE). A partial *legacy* payload can
  therefore still overwrite by position — unavoidable without an identity, and
  only pre-2026 JSON exports or an un-upgraded peer produce such rows.
* Merge hazards: the new suite section 4f posts to `/upload` without a CSRF
  token, so WP2's token check will need the test to send one; 4f also edits
  `noise_app.py` (`do_upload`, `do_import`, `upload_page`) and
  `templates/upload.html`, which WP2/WP6 touch too.

## WP2 notes and deviations (Opus)

* **`SESSION_COOKIE_SECURE` is an env flag, default on.** Both Pis are served
  over HTTPS through Cloudflare, so Secure is right there. But
  `deploy_to_pis.sh` advertises `http://192.168.1.116:5001` /
  `http://192.168.1.138:5001` for LAN use, and a Secure cookie is never sent
  over plain http — nobody can stay logged in on those URLs. An instance used
  that way must set `SESSION_COOKIE_SECURE=0` in `.env` and accept that the
  session cookie crosses the LAN in clear. Documented in `.env.example`.
* **The token reaches JavaScript through one shared include, not forty edits.**
  `templates/_csrf.html` publishes the token in a `<meta>` tag and wraps
  `window.fetch` once, adding `X-CSRF-Token` to same-origin non-GET requests.
  Deliberate on two counts: a `fetch()` added anywhere later is protected
  without anyone remembering, and it keeps this package out of WP4's way in
  `index.html`. Real HTML forms still carry a hidden `csrf_token` field.
* **The startup refusal lives in `noise_app`, not in `webauth`'s import.** The
  blueprints need `login_required` at import time, so `webauth` still defines a
  no-op one; `check_startup_security()` is what refuses, called from
  `noise_app` before the app object exists.
* **`test_modules.py` sets `ALLOW_UNAUTHENTICATED=1` at module scope** — the
  suite runs on a Mac with no flight-tracker auth module. Section 8 checks that
  a *subprocess* importing `noise_app` without it still exits non-zero, so the
  refusal is not neutered by the suite's own override.
* **`flask-limiter` was missing from `/tmp/nm-venv` and has been installed
  there.** The app imports it defensively: absent, `/login` and `/upload` are
  unlimited and a warning is logged rather than the app failing to start.
* **Deploy hazard.** The service now *refuses to start* if
  `/home/flightdata/flightdata/auth.py` cannot be imported, where before it
  would have come up serving everything publicly. Check
  `systemctl status noise-app` on both Pis on the first deploy after this
  lands; a failure there is the new behaviour working, not a regression.
* Not changed: `check_upload_auth()` still returns True when `UPLOAD_PASSWORD`
  is empty (now warned about at startup, per the brief); the API key is still
  accepted from a form field as well as the header, for the clients that post
  multipart.

## WP6 notes and deviations (Sonnet)

* **`init_db()` and `startup_sync_from_peer()` moved to module scope**, right
  after `MAX_CONTENT_LENGTH` is set and before the CSRF hook / rate limiter /
  blueprints are wired up, so they run on every import of `noise_app` —
  gunicorn's, `python3 noise_app.py`'s, and the test suite's. Both are
  idempotent (`init_db()` is `CREATE TABLE IF NOT EXISTS` plus additive,
  guarded `ALTER`s; `startup_sync_from_peer()` no-ops without `PEER_URL`/
  `IMPORT_API_KEY`), so this is safe to repeat across the suite's many
  `importlib` re-imports of the module. `sync_peer.py` and `import_sdcard.py`
  import `noise_db` directly, never `noise_app`, so they are unaffected.
  `__main__` now only calls `app.run(...)`.
* **`logging.basicConfig()` is the first executable statement in
  `noise_app.py`**, above even the `config`/`noise_db`/`webauth` imports, so
  it is in effect before those modules' own import-time log calls (e.g.
  `webauth`'s "auth module could not be imported" warning) rather than after.
* **The 413 handler renders inline rather than redirecting**, specifically so
  the response keeps status 413 — a redirect is always a 3xx, which would
  hide the failure from a client that checks the status code instead of
  reading the body. Browser form posts (the ZIP-upload path) get the upload
  page re-rendered with a flash message at 413; `/import`, `/api/*`, and the
  folder-upload `fetch()` call (which now sends `X-Requested-With:
  XMLHttpRequest`, added in `templates/upload.html`, so the handler can tell
  it apart from a plain form post) get a JSON body instead.
* **`get_db()`** now opens with `timeout=15` (SQLite's busy-timeout, so a
  writer waits rather than immediately raising "database is locked" under the
  concurrency gunicorn's 4 threads plus the weather/peer-push background
  threads create) and sets `PRAGMA journal_mode=WAL`. WAL means a running
  database is three files (`noise.db`, `-wal`, `-shm`), which is exactly why
  the backup step uses SQLite's own online-backup API and not `cp` — see
  `backup_db.py`'s docstring for what goes wrong with `cp` and the restore
  command.
* **Backups**: `backup_db.py` is a new, dependency-free script (only
  `sqlite3`/`gzip`/stdlib) rather than shelling out to the `sqlite3` CLI,
  since Gladys and Catherine already run two different Python interpreters
  and there was no reason to also depend on the CLI being on `PATH` for both.
  `setup.sh` installs `noise-backup.service`/`.timer` (daily 03:00, ±10 min
  jitter, `Persistent=true` so a backup still runs if the Pi was off at
  03:00). 14-day local rotation; best-effort `scp` of the newest backup to
  the peer's `/home/flightdata/backups/peer/`, gated on a new `PEER_SSH` env
  var — unset means local-only backups, which is the safe default (no new SSH
  trust relationship implied by just upgrading).
* **`deploy_to_pis.sh`** now runs `/tmp/nm-venv/bin/python3 test_modules.py`
  from `$LOCAL_DIR` before touching either Pi, aborting on failure;
  `--skip-tests` overrides with a printed warning, for when the test venv
  itself isn't available. The file list comes from `git ls-files` (already
  excludes `MEAS118/`, `*.zip`, `.env` via `.gitignore`; the script's own
  `grep -v` filter is defence in depth against a force-add) streamed through
  a single `tar` pipe rather than a hand-maintained `FILES`/`DIRS` pair of
  arrays plus a per-file `scp` loop — this is also what makes new files (like
  `backup_db.py` itself) show up on a Pi automatically. `VERSION` (`git
  rev-parse --short HEAD`) is written to `$REMOTE_DIR/VERSION` on every
  deploy, including `--setup`; `/health` reads it once at import time and
  reports `'dev'` when the file is absent (any checkout not deployed by this
  script, including this worktree). New `--pi Catherine|Gladys` restricts a
  run to one Pi.
* **gunicorn**: exactly 1 worker is load-bearing, not a starting point to
  tune up later — see the comment block above the `ExecStart=` line in
  `setup.sh` for why a second worker would silently double the in-memory rate
  limiter's counters and add a second SQLite writer process. `--threads 4`
  is what actually gives concurrency within that one worker.
* **Not done / left for later**: no `MAX_CONTENT_LENGTH` on the *peer sync*
  paths beyond what Flask already enforces globally (`/api/peer-sync-full`
  responses aren't separately capped — a very large full-sync payload from a
  compromised or buggy peer is still read entirely into memory); no
  structured/JSON log output, `format='%(asctime)s %(levelname)s %(name)s:
  %(message)s')` text only; `noise-backup.timer`'s `RandomizedDelaySec` means
  the exact backup time isn't 03:00 sharp on either Pi, which is intentional
  (avoids both Pis' nightly `scp` to each other landing in the same second)
  but worth knowing if a backup is ever timed against something else.

**WP8 outcome (branch `wp8-sessions-serial`, 3 code commits, suite 568/568 on
its base 81d2b42).** Built as specified; decisions and deviations:

* **Schema.** `sessions` is rebuilt (SQLite cannot swap `UNIQUE(date)` for
  `UNIQUE(date, instrument_serial)` in place): ids are copied so
  `runs.session_id` stays valid, `PRAGMA foreign_keys=off` guards the
  rebuild and is *verified* — if it cannot be disabled (a transaction is
  open) the migration raises `MigrationUnsafe` instead of letting
  `DROP TABLE sessions` cascade-delete every run. `deleted_sessions` PK
  becomes `(date, instrument_serial)` by rebuild; `assessment_runs` and
  `generated_reports` gain the column additively, backfilled with the

  `(assessment_id, session_date, instrument_serial, source_file)`.
  `weather` stays keyed by date (reference data), as scoped.
* **The default serial rules every legacy path.** `resolve_serial()` maps
  a missing *or blank* serial to the `instrument_serial` app setting (else
  `''`): old JSON exports, an un-upgraded peer's payloads and events,
  serial-less tombstones, pre-WP8 stored reports and every date-only URL
  all land on the default serial. Blank-equals-missing is deliberate — an
  empty serial is not a different instrument, it is an instrument nobody
  named.
* **Routes keep their URL shape.** `/session/<date>/…` takes `serial` as a
  query/body parameter; no redirects needed, every existing link works and
  means "the default meter". `?date=` deep links read `&serial=`;
  `manage.html` writes it. The upload form's serial field defaults to
  `last_upload_serial` (stored per upload) falling back to the
  `instrument_serial` setting; `/api/existing-dates` takes `?serial=` so the
  upload page's already-imported filter is scoped per meter.
* **Run tags got their stable key in passing.** The `run_tag` sync event and
  `/session/<date>/run/<n>/tag` now carry `source_file` (and the serial) and
  are applied by it when present — closing the WP1 "small follow-up" where a
  synced tag could land on the wrong run while the two Pis numbered a date
  differently.
* **Exporter.** `build_*`/`export_filename` prefer the serial passed in,
  else the run row's own `instrument_serial` (added by `get_full_run_row`);
  the route uses the session's serial and only falls back to the app
  setting for a session filed under a blank one.
* **Per-upload serial only**, per the decision: one SD card = one meter.
  Per-date-folder serial mapping inside one ZIP is not built.
* **Two pre-existing suite checks were updated**, both because a format
