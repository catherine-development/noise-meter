## Work packages

### WP1 — Run identity in the import path (F1, F2, F5) · Fable

Goal: a partial or re-ordered upload can never overwrite or shift a stored run.

1. `noise_db.import_sessions`: upsert runs on `(session_id, source_file)` (index
   `idx_runs_stable` exists); positional fallback only for rows with no `source_file`.
2. Assign `run_number` from the stored session order (sort by `source_file`
   within the session after upsert, renumber). `assessment_runs` already keys on
   `source_file`; WP3 makes reports do the same.
3. Stop writing `sessions.run_count / avg_laeq / max_laeq` from the payload; call
   `recompute_session_aggregates([date])` after the runs land.
4. Surplus rows: `parse_zip` reports per session whether the upload contained a
   complete date folder (`complete_date`); when true, runs absent from the
   payload are deleted; when false they are left alone.
5. Skips become visible: `parse_zip` returns skipped `(path, reason)` entries;
   `do_upload`, `/import` and `import_sdcard.py` surface them. The `>140`
   corruption check looks at every capped channel, not only ch1.
6. `push_to_peer` failures are logged at WARNING and recorded in `sync_state`
   (`last_push_error`), shown on the upload page.

Tests: partial upload preserves the other runs; re-import with a shifted first
run succeeds; assessment link follows the run through renumbering; skipped-file
report is populated; peer-push failure recorded.

**WP1 outcome (branch `worktree-agent-a6c18c3f58b2f3d83`, suite 275/275).**
Built as specified, with these decisions and deviations:

* Schema untouched. `UNIQUE(session_id, run_number)` stays on `runs`; new rows
  are inserted with `run_number NULL` and `_renumber_session_runs()` assigns
  1..n (by `source_file`, then `start_time`, then id) after every import. No
  table rebuild on the Pis.
* `complete_date` semantics are narrower than "delete what is absent": a
  session also carries `skipped_files` (PROJ folders present on the card but
  unreadable), and those are never deleted by a complete-date re-import. F2's
  scenario — first file now fails to parse — therefore keeps PROJ0001.
* Peer payloads (`get_sessions_since`, `get_sessions_export_format`) do **not**
  carry `complete_date`, so a pull or an admin push can only add or refresh
  runs on the receiving Pi, never delete. Deletions from a complete-date upload
  reach the peer only through `do_upload`'s direct `push_to_peer` of the parsed
  payload, which does carry the flag. Conservative on purpose; revisit in WP7.
* `do_upload` still skips a session whose run start times are all already
  stored, so a complete-date upload whose only difference is a *missing* run
  does nothing from the web UI; the deletion path is reachable through
  `/import` (import_sdcard.py `--push`), which has no such pre-check. Safe
  side; flagging rather than changing it here.
* `parse_zip`/`parse_files` return a `ParseResult` (list subclass) with a
  `.skipped` list of `{path, reason, date}`; `/import` returns it as `skipped`,
  `do_upload` appends it to the flash/JSON message (and stays on the upload
  page when there is one), `import_sdcard.py` prints it to stderr.
* `/import` now returns 409 with the constraint text on `IntegrityError`
  instead of 500; `push_to_peer` records `last_push_error` (JSON: at, dates,
  error) in `sync_state`, cleared on the next success, shown on `upload.html`.
  `push_to_peer` returns its thread so the suite can join it.
* Left as-is, deliberately: `update_run_location_tag`, `get_full_run_row`,
  `get_run_prof_laeq` and the `run_tag` sync event are still keyed on
  `run_number`. Numbers are re-read from the database on every render and both
  Pis number a date identically when they hold the same runs; they can diverge
  only while one Pi is missing a run for that date, in which case a synced
  location tag could land on the wrong run. WP4 adds a `source_file` route for
  prof data; carrying `source_file` in the `run_tag` event is a small follow-up.
* Legacy payload rows with no `source_file` still upsert positionally (the
  stored `source_file` is kept via COALESCE). A partial *legacy* payload can
  therefore still overwrite by position — unavoidable without an identity, and
  only pre-2026 JSON exports or an un-upgraded peer produce such rows.
* Merge hazards: the new suite section 4f posts to `/upload` without a CSRF
  token, so WP2's token check will need the test to send one; 4f also edits
  `noise_app.py` (`do_upload`, `do_import`, `upload_page`) and
  `templates/upload.html`, which WP2/WP6 touch too.

## WP2 notes and deviations (Opus)

* **`SESSION_COOKIE_SECURE` is an env flag, default on.** Both Pis are served
  over HTTPS through Cloudflare, so Secure is right there. But
  `deploy_to_pis.sh` advertises `http://192.168.1.116:5001` /
  `http://192.168.1.138:5001` for LAN use, and a Secure cookie is never sent
  over plain http — nobody can stay logged in on those URLs. An instance used
  that way must set `SESSION_COOKIE_SECURE=0` in `.env` and accept that the
  session cookie crosses the LAN in clear. Documented in `.env.example`.
* **The token reaches JavaScript through one shared include, not forty edits.**
  `templates/_csrf.html` publishes the token in a `<meta>` tag and wraps
  `window.fetch` once, adding `X-CSRF-Token` to same-origin non-GET requests.
  Deliberate on two counts: a `fetch()` added anywhere later is protected
  without anyone remembering, and it keeps this package out of WP4's way in
  `index.html`. Real HTML forms still carry a hidden `csrf_token` field.
* **The startup refusal lives in `noise_app`, not in `webauth`'s import.** The
  blueprints need `login_required` at import time, so `webauth` still defines a
  no-op one; `check_startup_security()` is what refuses, called from
  `noise_app` before the app object exists.
* **`test_modules.py` sets `ALLOW_UNAUTHENTICATED=1` at module scope** — the
  suite runs on a Mac with no flight-tracker auth module. Section 8 checks that
  a *subprocess* importing `noise_app` without it still exits non-zero, so the
  refusal is not neutered by the suite's own override.
* **`flask-limiter` was missing from `/tmp/nm-venv` and has been installed
  there.** The app imports it defensively: absent, `/login` and `/upload` are
  unlimited and a warning is logged rather than the app failing to start.
* **Deploy hazard.** The service now *refuses to start* if
  `/home/flightdata/flightdata/auth.py` cannot be imported, where before it
  would have come up serving everything publicly. Check
  `systemctl status noise-app` on both Pis on the first deploy after this
  lands; a failure there is the new behaviour working, not a regression.
* Not changed: `check_upload_auth()` still returns True when `UPLOAD_PASSWORD`
  is empty (now warned about at startup, per the brief); the API key is still
  accepted from a form field as well as the header, for the clients that post
  multipart.

## WP5 notes and deviations (Opus)

Built as specified. Suite 386 → 466 (new section 11a–11g); one existing check
changed, named below.

* **F8 — one weighted implementation, not three.**
  `noise_parser._energy_avg_weighted()` and `run_weight_s()` are the only place
  the combination rule lives; `parse_zip`, `noise_db._recompute_session_aggregates`
  and `reports._build_session_data_block` all call them. That means **`noise_db`
  now imports from `noise_parser`** — a new dependency direction, safe because
  `noise_parser` imports only `nor140_format`, and preferable to a third copy
  of the formula. Weight is `duration_s`, then `n`/`n_samples`, then 1.
* **F10 — the page had its own copy of the period rule.**
  `templates/assessments.html` carries a JavaScript `timePeriod()` that also
  returned Evening, so fixing only the Python would have left the run chips and
  the CSV disagreeing. Both are fixed, and the suite greps the template. The
  now-unreachable `--eve-*` CSS variables and `.chip-eve` / `.p-eve` / `.pp-eve`
  rules were left in place — inert, and removing them touches styling this
  package has no reason to touch.
  `spans_boundary` is True/False/None (None when the meter stored no end time —
  no arithmetic fallback, per the ground rules) and is surfaced as a
  `spans_boundary` column in the assessment CSV, blank when unknown. Both
  standards divide the day at 07:00 and 23:00, so one boundary set serves both.
  A run ending exactly on a boundary has not crossed it.
* **F11 — the shared percentile went into `noise_db`, not a new module.**
  A new `stats_util.py` would not have reached the Pis: `deploy_to_pis.sh` syncs
  a hand-maintained file list (WP6 replaces it with `git ls-files`, but WP5 must
  not depend on that landing first), so a new top-level module would have been
  an ImportError on deploy. `noise_db.percentile()` is public; `reports._percentile`
  is now an alias import of it, and `assessments_db` calls it directly. The
  assessment fallback reads `prof_lafspl_json`; where there is no stored series
  the percentiles are `None` rather than an estimate off the chart profile.
  On run 9 this moves the fallback LA10 from 75.5 to 74.9.
* **F12 — two of the three prices were wrong**, Opus 5 by a factor of three
  (15/75 against the real 5/25). Sonnet 5's introductory 2/10 rate (to
  2026-08-31) is noted in a comment and deliberately **not** encoded — a
  date-dependent price in that table starts lying on 1 September. The dated
  Haiku id is kept as an alias so stored reports still price. Also fixed
  beyond the brief: `templates/report.html` footed **every** report with
  "API usage (claude-sonnet-5)" regardless of the model that ran, which is a
  provenance error in an evidence document; it now reads `usage_info.model`.
* **F13 — `round_half_up` everywhere a dB is displayed or stored.** Two uses of
  Python `round()` survive on purpose and are named in the suite's guard: a
  compass-direction index and a USD cost, neither of which is a dB.
* **F13 — the spectrum reconstruction was kept, not deleted.** The handoff
  documents it as the verification that confirmed the spectral decode, so
  `_freq_weight_a/_c` and `_spectrum_total` remain, reachable through a new
  `noise_parser.spectrum_broadband(col, levels)`; what was deleted is the
  per-import computation of 36 `*_from_spectrum` values that no caller ever
  read. The IEC 61672 f4 pole is corrected from 12200 to 12194.217 Hz. Suite
  section 11f runs the handoff's own run-9 check through it (70.77 → LAeq 70.8,
  78.66 → LCeq 78.7). The −20.0-band asymmetry is noted in the docstring only.
* **Existing check changed:** section 4f's *"session avg recomputed from the
  remaining runs"* recomputed the expected value with the equal-weight formula
  and so encoded the old convention. It now computes the duration-weighted
  expectation from `duration_s`/`n_samples`, and a second check asserts the two
  formulas give measurably different answers for that date (~1 dB) so the
  change cannot be silently reverted. Nothing else in the suite encoded the old
  value — section 6b compares import against recompute rather than a literal,
  and now passes for a stronger reason than before.
* **Not changed:** `sessions.avg_laeq`'s column and CSV header names (`laeq_avg_db`),
  per WP4's note — D2 changes the definition, not the name. `nor140_format.py`
  is untouched apart from importing `round_half_up` from it.
* **Deploy hazard.** `recompute_session_aggregates()` must be run on both Pis
  after this deploys or stored sessions keep the old equal-weight value while
  newly imported dates get the new one. Documented in `docs/validation-brief.md`
  §10b with the exact command. **Not run.**
* **Merge hazards.** WP3 also edits `reports._prepare_session_for_report`,
  `api_generate_report` and `view_report`: WP5's change to `_prepare_session_for_report`
  is nil (it already summed real `duration_s` after WP4) — the run-row
  `duration_s` comes from `_run_stats`. In `api_generate_report` the only WP5
  edit is the `except` chain, fenced by `── WP5/F12 ──` comments; take WP3's
  snapshotting and keep the `BadRequestError → 400` clause. WP6 edits
  `noise_db.get_db` and `noise_app` startup — WP5 adds `percentile()` and two
  imports above `get_db`, so the two should not collide. New suite sections are
  appended at the end (11a–11g) and renumber nothing.
